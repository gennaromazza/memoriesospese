Analizza con estrema attenzione l’intero sistema blog composto da 3 componenti React/TypeScript collegati tra loro:

1. BlogManager (admin: creazione, modifica, preview, upload cover, salvataggio contenuto, delete, bulk actions)
2. BlogListPage (frontend pubblico: elenco articoli, ricerca, filtri, paginazione)
3. BlogPostPage (frontend pubblico: dettaglio singolo articolo, SEO, schema.org, social share, related posts)

NON modificare subito il codice.
Prima esegui una revisione tecnica approfondita dell’intero flusso applicativo, considerando i componenti non come file isolati ma come un unico sistema che coinvolge:
- React
- Firestore
- Firebase Storage
- dati BlogPost
- slug
- publishedAt
- content / contentUrl
- sicurezza HTML
- SEO
- UX
- coerenza dei dati tra admin e frontend pubblico

Voglio un’analisi prudente, accurata e production-oriented.
Per ogni osservazione devi spiegare:
1. se il problema è reale, parziale o non rilevante,
2. perché lo è,
3. che impatto ha,
4. quanto è urgente,
5. qual è la soluzione migliore,
6. quali compromessi o effetti collaterali comporta.

Solo dopo l’analisi completa dovrai proporre le modifiche.

I punti da verificare sono questi.

1) Coerenza complessiva del modello dati BlogPost
Verifica se i tre componenti assumono in modo coerente la struttura del documento blog:
- id
- title
- slug
- excerpt
- content
- contentUrl
- coverImage
- status
- category
- tags
- author
- metaTitle
- metaDescription
- createdAt
- updatedAt
- publishedAt

Analizza se ci sono assunzioni incompatibili tra admin e frontend e se alcuni campi vengono trattati come obbligatori in un componente ma opzionali in un altro.

2) Campo id: persistito o solo lato client
Verifica se il sistema conferma che id non è salvato realmente nel documento Firestore ma viene aggiunto lato client usando doc.id.
Analizza le implicazioni sul componente BlogPostPage, che nella logica related posts usa una query come where('id', '!=', currentPost.id).
Spiega se questa assunzione è errata e qual è la correzione giusta.

3) Gestione di content e contentUrl
Analizza in profondità la strategia dati:
- contenuti piccoli salvati inline in content,
- contenuti grandi salvati su Firebase Storage con contentUrl,
- contenuto svuotato nel documento quando viene usato contentUrl.

Verifica se questa strategia è coerente nei tre componenti:
- BlogManager crea contentUrl,
- BlogPostPage lo legge e fa fetch del contenuto,
- BlogListPage invece sembra ignorarlo.

Spiega se questa incoerenza genera bug funzionali, soprattutto sul tempo di lettura, ricerca, preview o rendering.

4) Tempo di lettura incoerente in tutto il sistema
Verifica le implementazioni di estimateReadTime nei tre componenti.
Analizza:
- se contano HTML invece che testo reale,
- se i post con contentUrl producono tempi di lettura errati o nulli,
- se il formato restituito è incoerente tra lista, dettaglio e preview,
- se conviene creare una utility condivisa unica.

5) Sicurezza HTML / rischio XSS
Analizza tutti i punti in cui viene usato dangerouslySetInnerHTML:
- preview admin,
- pagina dettaglio articolo,
- eventuali altri punti indiretti.

Verifica:
- se il rischio XSS è reale,
- quanto è grave,
- se il contenuto proveniente da ReactQuill / import / storage debba essere sanitizzato,
- dove conviene sanitizzare,
- se la stessa policy di sanitizzazione debba essere applicata in admin e frontend.

6) Query Firestore e coerenza logica
Verifica tutte le query dei tre componenti:
- query per post pubblicato tramite slug,
- query per lista post pubblicati,
- query per related posts,
- query controllo unicità slug.

Analizza:
- se sono corrette,
- se sono fragili,
- se richiedono indici specifici,
- se esistono query concettualmente sbagliate,
- se alcune query fanno assunzioni non vere sui dati salvati.

7) Query lista blog: status + publishedAt != null + orderBy
Nel BlogListPage viene usata una query che combina:
- where(status == published)
- where(publishedAt != null)
- orderBy(publishedAt desc)

Analizza:
- se questa query è davvero necessaria,
- se è fragile,
- se publishedAt dovrebbe essere garantito già dal modello dati,
- se potrebbe creare problemi di indice,
- se conviene semplificarla oppure lasciare un doppio filtro difensivo.

8) Semantica reale di publishedAt
Verifica se publishedAt ha lo stesso significato in tutto il sistema.
Analizza:
- nel salvataggio singolo admin sembra indicare la prima pubblicazione,
- nella bulk publish admin viene sovrascritto sempre,
- nel frontend pubblico viene mostrato come data editoriale e usato per ordinamento e schema.org.

Spiega se questa è una contraddizione reale e quale semantica va mantenuta:
- prima pubblicazione,
- ultima pubblicazione,
- oppure altra logica esplicita.

9) Integrità dello slug e unicità reale
Il manager verifica l’unicità dello slug con una query prima del salvataggio.
Analizza:
- se questo controllo sia sufficiente o solo probabilistico,
- se esiste rischio di duplicati in concorrenza,
- come questo rischio impatta il BlogPostPage che carica per slug e prende il primo risultato,
- quale strategia robusta sarebbe preferibile.

10) Fallback e robustezza dei campi stringa
Verifica se ci sono punti in cui il codice assume che campi come:
- title
- excerpt
- author
- category
- tags
siano sempre presenti e validi.

Analizza:
- possibili crash o warning con documenti legacy o incompleti,
- uso di toLowerCase su campi potenzialmente undefined,
- input controllati che potrebbero ricevere undefined,
- necessità di fallback coerenti.

11) formatDate troppo rigida
Verifica le funzioni formatDate nei componenti pubblici.
Analizza se gestiscono solo timestamp Firestore con property seconds.
Spiega:
- se siano troppo rigide,
- se possano rompersi con Date native, stringhe ISO o serializzazioni differenti,
- se convenga centralizzare anche questa logica.

12) Import duplicati, import inutilizzati e pulizia generale
Verifica in particolare nel BlogManager:
- import duplicati di storage, ref, getDownloadURL,
- eventuali import inutilizzati come CheckSquare, InsertBlogPost o altri.

Analizza se ci siano problemi reali di build e se serva una pulizia sistematica.

13) Salvataggio contenuto grande con ID provvisorio
Nel manager, per nuovi post con contenuto grande, il file HTML su Storage viene salvato con un identificativo temporaneo tipo new-timestamp, mentre il documento Firestore viene poi creato con addDoc e riceve un altro ID.
Analizza:
- se questo genera solo naming incoerente o anche problemi di tracciabilità,
- se convenga generare prima l’ID del documento.

14) File orfani su Firebase Storage
Analizza la gestione lifecycle dei file:
- contenuto HTML su Storage quando un post passa da grande a piccolo,
- cover image caricata su Storage,
- eliminazione di un post.

Verifica se il sistema lascia file orfani su Storage.
Spiega:
- quanto è grave nel tempo,
- se la pulizia debba essere fatta lato client, lato server o con job separati.

15) openDialog asincrono e possibili race condition
Nel manager, aprendo un post con contentUrl, viene fatto un fetch asincrono del contenuto prima di valorizzare il form.
Analizza:
- se esiste rischio di race condition,
- se chiudendo o cambiando rapidamente post si possano avere update fuori tempo,
- quale strategia di protezione convenga usare.

16) loadPosts e gestione degli stati loading/error
Analizza come i tre componenti gestiscono loading ed error.
Verifica:
- se loadPosts del manager reimposta loading in modo corretto,
- se nel frontend pubblico eventuali errori vengono comunicati all’utente o solo loggati,
- se la UX di caricamento/errore sia coerente e sufficientemente robusta.

17) Related posts: correttezza logica e scalabilità
Analizza la logica related posts del BlogPostPage:
- query su published,
- esclusione del post corrente,
- filtro per category o tag,
- slice finale.

Verifica:
- se oggi è corretta,
- se il bug su id la rende sbagliata,
- se la soluzione sia da fare lato query o lato client,
- se la strategia scala bene o no.

18) Ricerca e filtri nel BlogListPage
Analizza:
- ricerca su title/excerpt,
- filtri category/tag,
- paginazione,
- reset pagina al cambio filtro,
- robustezza con dati mancanti,
- normalizzazione di category e tags.

Verifica se esistono bug funzionali o rischi di UX confusa.

Analizza:
- se è un comportamento corretto,
- se è ambiguo lato UX,
