🐞 Bug e problemi rilevati
1. Memory leak da URL.createObjectURL mai revocate
Posizione: createPreviews (non chiamata) e inizializzazione progress in onDrop / mutationFn.
Problema: Ogni anteprima genera un Object URL che non viene mai rilasciato con URL.revokeObjectURL(). Questo consuma memoria inutilmente, specialmente con molti file.
Soluzione:

Aggiungere useEffect per ripulire gli URL quando uploadProgress cambia o il componente si smonta.

Esempio:

tsx
useEffect(() => {
  return () => {
    uploadProgress.forEach(p => p.preview && URL.revokeObjectURL(p.preview));
  };
}, [uploadProgress]);
2. Possibili upload sovrapposti e corruzione dello stato
Posizione: onDrop chiama uploadMutation.mutate() senza controllare se un upload è già in corso.
Problema: Se l’utente trascina altri file mentre il primo upload è ancora attivo, la nuova mutazione reimposta uploadProgress (lo fa all'interno della mutationFn), cancellando il progresso precedente e creando conflitti.
Soluzione:

Disabilitare la dropzone / il pulsante di upload quando uploadMutation.isPending è true.

Aggiungere un messaggio visivo (“Upload in corso, attendere…”).

Opzionalmente, accodare nuovi file invece di scartarli, ma è più complesso.

3. Rilevamento duplicati potenzialmente obsoleto durante upload rapidi
Posizione: La mutazione usa existingPhotoNames e existingPhotoHashes dallo state.
Problema: Dopo un upload, il refetchQueries aggiorna allPhotos in modo asincrono; se l’utente avvia subito un nuovo upload, la lista dei duplicati potrebbe non includere le foto appena caricate. Il controllo backend probabilmente li blocca, ma lato client sarebbe meglio avere dati freschi.
Soluzione:

All’interno della mutationFn, invece di usare lo state, leggere i dati correnti da queryClient.getQueryData(['gallery-photos', galleryId]) e derivare i set di nomi/hash.

Oppure invalidare la query prima di procedere con l’analisi duplicati, per essere sicuri di avere l’ultimo stato.
